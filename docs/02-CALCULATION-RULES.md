# Правила подсорта в бэкофис-системе StockFlow

Исходная рабочая книга использовалась для подсорта товаров нескольких селлеров. Она не публикуется: в ней есть данные клиентов.

## Что делали до StockFlow

Из личных кабинетов маркетплейсов получали продажи и остатки. Книга сопоставляла товар с выгрузками, суммировала продажи по неделям, переводила остаток площадки в дни покрытия и предлагала количество к пополнению. Для разных категорий и площадок использовали разные целевые сроки запаса. Итог корректировали коэффициентами и округляли.

В основных листах книги стояло условное ограничение `9999`. Фактический остаток мы отдельно сверяли с системой или таблицей селлера.

## Как правила работали в сервисе

| Правило | Поведение StockFlow |
| --- | --- |
| Источник данных площадок | StockFlow автоматически получал продажи и остатки через API маркетплейсов, показывал время последнего обновления и ошибки синхронизации. Данные собственного склада поступали отдельно из учёта селлера. |
| Темп продаж | Менеджер видел продажи за выбранное окно и рассчитанный дневной темп рядом с предложением. При отсутствии данных количество не подменялось нулём без пояснения. |
| Целевой запас | Дни покрытия настраивались по селлеру, маркетплейсу и категории товара. В плане сохранялась использованная версия правила. |
| Рекомендация площадке | StockFlow показывал остаток на площадке, целевой запас и рекомендуемое пополнение по товару. Это значение не считалось доступным к отгрузке и не требовало обязательного утверждения. |
| Свой склад | Перед каждым утверждением менеджер заново подтверждал доступное количество из учёта селлера. Для предложения и решения сохранялся отдельный снимок; большое условное число из книги не использовалось как остаток. |
| Дефицит | Когда своего товара не хватало, сервис предлагал распределить доступное количество пропорционально рассчитанной потребности площадок. Менеджер мог изменить это распределение перед утверждением. |
| Закупка | Недостающий объём выводился отдельным предложением по заказу поставщику, а не прибавлялся к плану уже доступной отгрузки. |
| Решение менеджера | Менеджер мог принять рекомендацию, изменить количество или отклонить её по своей стратегии. Система сохраняла исходный расчёт и принятое решение; отклонение не создавало план отгрузки или закупки. |

У снимка собственного склада не было фиксированного срока действия. Требовалось **новое подтверждение менеджера для каждого утверждения**: снимок, уже использованный в утверждённом плане, нельзя было повторно взять как подтверждение для следующего. StockFlow принимал доступное количество, которое менеджер сверил в учёте селлера.

## Расчёт потребности площадки

Для базового сценария без товара в пути и дополнительных коэффициентов:

- `дневной темп = проданные единицы / число календарных дней окна`;
- `целевой запас = дневной темп × целевые дни покрытия`, приведённый к целым штукам по `roundingPolicy` сохранённой версии правила;
- `потребность = max(0, целевой запас − остаток площадки)`.

Границы окна продаж включаются в расчёт: `число дней = periodEnd − periodStart + 1`. Подтверждённые нулевые продажи дают нулевую потребность; дни покрытия при нулевом темпе не вычисляются делением на ноль. Округление целевого запаса и распределение дефицита — разные правила: второе всегда использует метод наибольших дробных остатков.

`dataState` описывает наличие снимков продаж и остатка. Даже при `dataState: ready` расчёт невозможен без версии правила: тогда количество равно `null`, в `calculationIssue` указана причина, а вся рекомендация имеет статус `incomplete`. Такая рекомендация доступна для просмотра и отказа, но не для распределения и утверждения. Дополнительные коэффициенты, товар в пути и кратности отгрузки в описанный контракт не входят.

## Как распределялся дефицит

Для одного внутреннего товара `потребность площадки` — это рассчитанная рекомендация до учёта собственного склада. Если доступного своего товара меньше суммарной потребности, StockFlow формировал **начальное предложение**, а не окончательный план:

1. Для каждой площадки рассчитывал долю: `доступный остаток × потребность площадки / суммарная потребность`.
2. Сначала брал целую часть каждой доли. Оставшиеся штуки по одной отдавал площадкам с наибольшей дробной частью. При равной дробной части использовал стабильный порядок идентификаторов товаров площадок, чтобы результат не зависел от порядка строк на экране.
3. Недостающий объём показывал отдельно: `суммарная потребность − распределённое количество`. Он становился **предложением по закупке**, а не товаром для текущей отгрузки.

Если своего товара хватает на всю потребность, предложение по отгрузке равно рассчитанной потребности каждой площадки, закупка по этому расчёту равна нулю, а лишний остаток остаётся на своём складе. При нулевой суммарной потребности отгрузка и предложенная закупка также равны нулю. При неполных данных площадки предложение распределения не формируется до устранения причины: отсутствие данных нельзя трактовать как нулевую потребность.

Например, потребность Ozon — 9 шт., Wildberries — 34 шт., всего — 43 шт., а на своём складе доступно 30 шт. Доли составляют примерно 6,28 и 23,72 шт. После распределения последней целой штуки начальное предложение — **6 шт. для Ozon и 24 шт. для Wildberries**; ещё **13 шт.** показаны к закупке. Менеджер в [сквозном сценарии](04-USE-CASE.md) изменил предложение на 9 и 21 шт. перед утверждением. Сервис сохранил исходное предложение и итоговые количества менеджера отдельно.

## Что не переносили из книги без проверки

- Значения целевого покрытия `45`, `75`, `80` и `90` дней встречались в проверенных листах Ozon и Wildberries. Они стали примером настроек, а не общим нормативом для всех селлеров.
- Множитель `0,2` встречался в части строк Ozon, но его смысл по повреждённым подписям нельзя подтвердить. StockFlow не применял неизвестный коэффициент скрыто.
- Старая формула округления могла дать `3` при расчётном количестве около `3,857`, несмотря на записанный порог `0,6`. В сервисе способ округления был отдельной видимой настройкой; ошибочную формулу не копировали.

Таким образом, книга послужила источником задач и примеров, но не была техническим контрактом сервиса. Предложение StockFlow можно было проследить от данных API и настроек до решения менеджера — утверждения, изменения или отклонения.
