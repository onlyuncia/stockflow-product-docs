# Нефункциональные требования StockFlow

Таблица задаёт проверки реконструированной архитектуры. Она не является отчётом о нагрузочном испытании или подтверждением характеристик эксплуатируемого сервера. Ограничения количества и история проверяются также в синтетическом прототипе; серверные проверки нужно выполнять на реализации HTTP API и PostgreSQL.

## Целостность, доступ и надёжность

| ID | Требование | Проверка |
| --- | --- | --- |
| НФТ-01 | Чтение и изменение доступны только пользователю, имеющему доступ к соответствующему селлеру. Проверка касается каждого кабинета, листинга, снимка и решения. | Попытки получить или связать ресурсы другого селлера через URL и тело команды. Механизм входа и матрица ролей выбираются отдельно; текущий OpenAPI их не утверждает. |
| НФТ-02 | Проверки утверждения и сохранение решения со всеми планами выполняются атомарно. | Ошибка до записи и между записями не оставляет частичного результата в БД. |
| НФТ-03 | У рекомендации только одно итоговое решение; использованное в утверждении подтверждение собственного остатка не используется повторно. | Два конкурентных запроса: один сохраняет результат, другой получает конфликт; повторное чтение возвращает первоначальное решение. |
| НФТ-04 | Поздняя синхронизация и изменение правил не меняют входы и результат уже принятого решения. | Повторить чтение истории после нового снимка или рекомендации; ссылки и количества исходного решения остаются прежними. |
| НФТ-05 | Недоступность источника и подтверждённый ноль различимы; неполный расчёт не становится исполнимым планом. | Таймаут площадки, отсутствие продаж, отсутствие версии правила, подтверждённые нулевые продажи. |
| НФТ-06 | У каждого обновления видны кабинет, тип данных, время начала и завершения, результат и причина ошибки. | Для снимка можно восстановить `SyncRun`; неуспешное обновление не скрывает ошибку за новым временем успешности. |
| НФТ-07 | Для каждого итогового решения сохраняются автор, время, входные ссылки и утверждённые количества либо причина отказа. | Восстановить решение без обращения к текущему состоянию карточки товара. Срок хранения устанавливается политикой владельца; материалы не подтверждают конкретный срок. |
| НФТ-08 | Ошибки команд содержат стабильный машинный код и понятное сообщение; числа не исправляются молча. | Проверить `400`, `404`, `409`, `422`, отрицательное и дробное количество, пустой ввод, повтор позиции. |

## Целевые показатели проверки интерфейса и API

Для воспроизводимого испытания принят **целевой**, а не исторический профиль: 5 одновременных сеансов, до 10 000 внутренних товаров и 10 подключённых кабинетов. Это профиль проверки реконструкции; число пользователей и товаров в эксплуатации определяется отдельно.

| ID | Предлагаемый норматив | Как измерять |
| --- | --- | --- |
| НФТ-09 | Чтение первой страницы из 50 рекомендаций через внутренний API - не более 2 с, p95; готовность интерфейса к работе - не более 3 с, p95. | Прогретый сервис, указанный профиль, не менее 200 запросов. Внешние API и ожидание новой синхронизации измеряются отдельно. |
| НФТ-10 | Серверная проверка и сохранение решения по одному товару с двумя площадками - не более 2 с, p95. | Не менее 200 команд, отсутствие вызова внешней площадки внутри транзакции утверждения. |
| НФТ-11 | На ширине 320 CSS px выбор товара и принятие решения доступны без горизонтального расширения страницы. | Проверить подтверждение остатка, изменение, отказ, историю и планы. Широкие диаграммы прокручиваются в отдельном просмотрщике. |
| НФТ-12 | Основные действия доступны с клавиатуры; фокус видим, ошибки формы связаны с полями, движение можно уменьшить настройкой системы. | Полный сценарий клавиатурой, проверка фокуса диалога и режима уменьшения движения. |

Цифры НФТ-09–НФТ-10 не включаются в бизнес-результаты до измерения. Доступность сервера, резервное копирование и восстановление требуют эксплуатационной политики: для них не заявляются неподтверждённые SLA, RPO или RTO.
